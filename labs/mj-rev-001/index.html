Tracing a Password Checker in GDB

A lab template for following user input through an x86-64 ELF and locating the branch that decides success or failure.

Objective

Determine how a small password-checking program validates input, identify the decisive conditional branch, and record a workflow that can be repeated on similar binaries.

Environment

OS       Ubuntu 24.04
Format   ELF 64-bit LSB, x86-64
Tools    file, strings, GDB, pwndbg, Ghidra

Initial observations

Start with low-cost triage: inspect the file type and security properties, run strings, then execute the binary with clearly different inputs. The goal is to form testable hypotheses before opening a disassembler.

Static analysis

Locate references to the success and failure strings, then walk backward through their cross-references. In a simple checker this typically leads to a comparison call or loop and the conditional jump controlling the result.

file ./checker
strings -a ./checker
objdump -d -M intel ./checker | less

Dynamic analysis

Break before the comparison, provide a known input, and inspect argument registers under the System V AMD64 ABI. Step across the call and observe the return value and flags before the following branch.

break main
run
disassemble /m main
info registers
x/s $rdi
x/s $rsi

Key findings

The useful result is not merely a recovered password. It is the chain of evidence connecting input, comparison arguments, return value, flags, and the branch that selects program output.

Lessons learned

  • String cross-references provide fast orientation in small binaries.
  • Calling conventions turn register values into meaningful program data.
  • Static and dynamic views are most useful when they test each other.
